# Injection-point analysis (`I-*`)

[Report index](README.md)

Method: every `@Query` (JPQL and `nativeQuery`), every `JdbcTemplate.update`, every
`LIKE`/`ORDER BY` path, and every DB-sourced output channel in `src/` and `bot/`
was enumerated and checked for string-built SQL or unsanitized interpolation.

---

## I-1 — SQL injection: none found (Info — positive result)

Every raw SQL statement in the codebase uses **bound parameters** (`?` /
`:name`). Complete inventory:

| Location | Statement | Binding |
| --- | --- | --- |
| `FavouriteRepository.insertIfAbsent` | `INSERT INTO favourites … ON CONFLICT DO NOTHING` | `:userId`, `:postId` |
| `NotificationOutboxRepository.insertIfAbsent` | `INSERT INTO notification_outbox … ON CONFLICT (dedupe_key) DO NOTHING` | `:dedupeKey`, `:type`, `:recipient`, `:payload`, `:aggregateId`, `:nextAttemptAt`, `:createdAt` |
| `PostRepository.archiveExpiredPosts` | `WITH expired AS (… LIMIT 100) UPDATE posts …` | `:now` only; `LIMIT 100`, status literals are constants |
| `RateLimitFilter.consumeSharedBudget` | `INSERT … ON CONFLICT (rate_key) DO UPDATE …` | `?` ×3 (key, timestamp, limit) |
| `CredentialCleanupScheduler.cleanExpiredCredentials` | `DELETE FROM api_rate_limit_windows WHERE window_start < ?` | `?` ×1 |

All 20+ JPQL `@Query`s use named parameters; the enum literals embedded in JPQL
(`com.studentstorefront.enums.PostStatus.ACTIVE`, `ReviewDirection.SELLER_TO_BUYER`,
`WhatsAppSessionStatus.EXPIRED`) are compile-time constants, not input. Derived
query methods (`findByUserUserIdAndIdempotencyKey`, etc.) are generated by Spring
Data from typed parameters. **There is no user input concatenated into any query.**

Note on `notification_outbox.payload`/`last_error`: these are stored attacker-adjacent
strings (titles, error messages) but are only read back as data — never executed.

## I-2 — LIKE/wildcard injection: defended, but the defense is duplicated (Low)

**Where:** `PostService.searchAvailablePosts` + `PostService.escapeLike`, and
`UserService.searchEnabledUsersByName` + `UserService.escapeLike` (identical copies);
queries use `LIKE LOWER(CONCAT('%', :query, '%')) ESCAPE '!'`.

**Assessment:** `%`, `_`, and the `!` escape char are properly escaped in both
paths, so a search for `%` or `__` cannot turn into a table-wide wildcard scan or
wrong matches. This is correct.

**How it is wrong/unoptimal:** the escape function and the `ESCAPE '!'` literal are
copy-pasted in two services. The next search feature (e.g. searching reviews,
messages, or buyer names) that forgets the copy will reintroduce wildcard
amplification (a `%` query on an unindexed `LIKE` becoming a forced full scan — a
cheap DoS lever, per P-8). Centralize `escapeLike` + a `containsPredicate` helper
in one place and lint for raw `LIKE` construction.

## I-3 — ORDER BY injection: defended via allowlists (Info — positive, with nits)

**Where:** `PostService.safePageable` (allows `createdAt, postId, price, title,
category, status`; appends a `postId` tiebreaker for stable pagination),
`UserService.safePageable` (`userId, name, createdAt, isEnabled`; `userId`
tiebreaker). All other endpoints (`FavouriteService`, `ReviewService`, `SaleService`)
use hardcoded sorts.

**Assessment:** Spring would block property traversal into associations on its own,
and these explicit allowlists make it airtight — no `JpaSort.unsafe` anywhere.
Stable tiebreakers are a correctness plus (no page-skipping under equal sort keys).

**Nits:** the two allowlists are duplicated (same maintenance hazard as I-2);
allowing `status`/`title` sorts is unnecessary surface (any column can be the sort
key today — a future column with sensitive cardinality would leak ordering side
channels); unbounded `pageNumber` still permits deep-OFFSET scans (P-7).

## I-4 — Stored XSS via database fields: no sink today, fragile contract (Low)

**Data at risk:** `users.name`, `posts.title`, `posts.description`, `reviews.comment`,
`post_media.media_url`, plus outbox message bodies assembled from these fields.

**Channels checked:**
- Frontend (`src/main/resources/static/**`): grep for
  `innerHTML|insertAdjacentHTML|document.write|eval|new Function` → **no matches**.
  Alpine.js text/attribute bindings escape by default, and no `x-html` usage was
  found in the app JS.
- Email (`EmailService`) and WhatsApp (`BotNotificationService` payloads, bot
  templates): plain-text channels — no HTML/script interpretation.
- `JwtAuthenticationFilter`/`RateLimitFilter` write **constant** strings into their
  hand-rolled JSON responses (no user data interpolated) — no JSON-injection there.

**How it is wrong/unoptimal anyway:** nothing *forbids* a future template from
rendering `description`/`comment` with `x-html` or building the hand-rolled JSON
error bodies with interpolation (the pattern in those two filters invites it).
There is also no output-encoding policy documented next to the DTOs. One careless
`x-html="post.description"` turns this DB into a stored-XSS distribution channel
for every marketplace visitor.

**Fix:** document the "always `x-text`/escaped" rule for DB-sourced strings; make
the hand-rolled filter responses use a serializer; consider stripping control
chars from `name`/`title` at write time (also helps WhatsApp/email rendering).

## I-5 — SSRF residue on media URLs: write-time-only validation (Low/Medium)

**Where:** `MediaUrlPolicy.validate` (write-time DNS + address-class check) vs the
bot's later fetch of stored `media_url`s (`bot/src/services/safeRemoteMedia.js`,
`WhatsAppShoppingChat` detail flow).

**Assessment:** the write path is solid (HTTPS-only, no userinfo, no
localhost/`.local`, rejects any/loopback/link-local/site-private resolved
addresses — closing the previous audit's SSRF finding at the API layer). But the
DNS check happens at **store time** while the fetch happens **much later**; a
domain that resolved public at insert can rebind to `169.254.169.254`/internal
hosts when the bot fetches it (DNS rebinding TOCTOU). Whether that matters depends
on the bot's own fetch hardening, which is outside the DB layer — but the DB is the
component that vouches for the URL.

**Fix:** have the bot re-validate scheme/host/address classes (and redirects) at
fetch time and enforce size/time limits; optionally restrict stored URLs to the
known media provider hosts (`res.cloudinary.com`) instead of "any public HTTPS host".

## I-6 — Other injection classes checked (Info)

- **Second-order SQL:** DB values reused in queries only as bound parameters
  (`markReminderSentIfPending(aggregateId, …)`, dedupe keys) — safe.
- **HTTP header/log injection:** `NotificationOutbox.last_error` stores capped
  (`take(1000)`) exception messages; no user-controlled header is echoed into DB
  or logs verbatim except `creator_ip` (V-4/D-1, low risk).
- **Email header injection:** recipients come from `users.email` (pattern-validated
  `@Email` + campus regex) and are passed as `SimpleMailMessage` recipients, not
  raw headers — no CRLF path found.
- **Expression/template injection:** no SpEL/EL evaluation of DB strings; LLM output
  in the bot is parsed as data (`parseJsonFromLlmText`) and lands in the DB only via
  the validated REST DTOs (`PostRequestDTO` constraints + service checks).
- **Path traversal via DB values:** media filenames never derive from DB content on
  the backend (Cloudinary `public_id` is provider-issued); temp files use
  `Files.createTempFile` with a fixed prefix (the old `originalFilename`-concatenation
  traversal is fixed — see 08-superseded-findings.md).
